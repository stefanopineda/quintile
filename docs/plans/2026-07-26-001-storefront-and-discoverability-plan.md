## What we optimize for

1. **Utility** — does the product do a real job better for its users?  
2. **Ease of use** — install → first useful tile without a human tutor  
3. **Ease of discoverability** — can the right person understand and find it quickly?

Make something great. Make the differentiator obvious. Tell people. Everything else is downstream.

## Scope (three moves)

| Move | Job |
|------|-----|
| **A** | README as a 5-second demo reel (utility + discoverability) |
| **B** | Differentiator-first announce drafts (discoverability when *you* post) |
| **C** | Optional amplifier outreach kit (discoverability via people who already write for the audience) |

**Sequence:** A on `main` before any public announce. B/C are human-owned posts/DMs after merge.

**Out of scope:** feature churn for attention, scoreboard CTAs, app code changes in this branch.

## Phase A — README

- Differentiator headline + for/not-for + laptop honesty  
- All demos: hero, grid-select, presets, profiles  
- Install: tap path primary; official cask status factual, not a campaign  
- Issues link for real feedback  

## Phase B — Announce drafts (not auto-posted)

- Hook: two-cell span (`⌃⌥G`), not “another tiler”  
- Channels when *you* choose: X, r/MacApps, optional Show HN  
- Media: `docs/demos/grid-select.gif`  

## Phase C — Amplifier kit (not auto-sent)

- ≤10 people who cover Mac window tools  
- Packet: demo + one sentence + install — no vanity asks  

## Definition of done for this branch

- README and marketing drafts reviewed by you  
- Pre-merge test steps pass (see `docs/marketing/BRANCH_REVIEW.md`)  
- Merge only when you are satisfied the storefront helps real users  

Announce and outreach happen *after* merge, when you decide the work is good enough to show.
